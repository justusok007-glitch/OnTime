# Staff Attendance System – Final Specification

- **Android app:** Kotlin, CameraX, ML Kit (QR scanning), Room, WorkManager, Supabase SDK
- **Admin:** Web app (React + Vite), hosted free on **GitHub Pages**
- **Backend:** Supabase Free Plan (Auth, Postgres, Storage, Edge Functions, scheduled jobs)
- **Build & distribution:** GitHub Actions builds the APK; staff download it from GitHub Releases

---

## 1. Individual Login

- The admin creates each account with an ID (T001) and a password. There is no self sign-up.
- Internally, each ID is mapped to an email such as `t001@alfurqan.local`, because Supabase Auth requires one. Staff only ever type "T001".
- The first login must be online. After that, the session stays cached so attendance works offline.
- A fingerprint or PIN unlock is required before each attendance.
- The admin can reset passwords and deactivate accounts.

## 2. Device Binding and Verification

- On first login, the app creates a key pair inside Android Keystore. The private key never leaves the phone.
- The public key, phone model and registration date are stored on the server.
- Every attendance record is signed with the private key. A server function rejects any record that isn't signed by that staff member's registered device.
- **Device security check:** Keystore Key Attestation (proves the key is hardware-backed) plus root detection.
  - *Optional:* if the app is distributed through Play Console internal testing ($25 one-time), Play Integrity can be added as an extra check.
- The admin can revoke a device, approve a replacement and view device history.

## 3. QR Code (Permanent, with Regenerate)

- One printed QR code is placed at the entrance. It contains: school code, QR version number, random token and a server signature.
- The app checks the signature offline, so a fake or random QR is refused immediately.
- **Admin "Regenerate QR" button:**
  1. A new token is created and the version number goes up (v1 → v2).
  2. The old QR stops being valid from that moment.
  3. A printable A4 PDF downloads to the admin's device. It contains the large QR code, school name, "Staff Attendance – Scan Here", the version number and the date generated.
- Every record stores which QR version was scanned. If a phone was offline during a regeneration and scans the old QR afterwards, that record is flagged "Old QR" in reports.
- The QR history (version, generated by, date) is kept in the audit log.

## 4. Automatic Photograph

- After the QR scan, the front camera opens and captures automatically. There is no gallery access.
- Two images are saved:
  - **Original:** the clean photo, kept for verification.
  - **Overlay copy:** school name, staff name and ID, date, time, location status, device status and attendance reference (e.g. AT-10025).
- The overlay time is labelled "Device time". The server time is stored separately after sync.
- Each photo gets a unique reference and a SHA-256 hash. A photo whose hash matches an earlier record is flagged "Duplicate photo".
- Photos are compressed to about 100–150 KB each to stay within free storage.

## 5. GPS Recording (No Auto Accept/Reject)

- The app records latitude, longitude, accuracy, distance from the academy, location time and mock-location detection.
- **The rule:**
  - Distance ≤ 100 m → saved as **"In Range – 42 m"**
  - Distance > 100 m → saved as **"Out of Range – 350 m"**
  - Mock location detected → additionally marked **"Fake GPS suspected"**
- Attendance is always saved. The app never accepts or rejects it.
- The distance and status appear in the admin reports and in the teacher's own attendance menu.
- The admin can change the academy coordinates and the 100 m radius from the web app.

## 6. Offline Attendance and Sync

- Records are saved in an encrypted Room database. Each record holds:

| Field | Purpose |
|---|---|
| Transaction ID | Unique attendance reference |
| Staff ID | Employee identification |
| Device ID | Authorized device reference |
| Event Type | Check-in / Check-out |
| Device Time | Local recorded time |
| Uptime Counter | Time evidence independent of phone clock |
| GPS Lat / Long / Accuracy | Location |
| Distance + Range Status | In Range / Out of Range |
| Image Paths + Hash | Photos and duplicate detection |
| QR Version | QR verification |
| Signature | Device verification |
| Sync Status | Pending / Synced / Flagged |

- WorkManager uploads pending records automatically when internet returns. It retries on failure and resumes interrupted uploads.
- There is also a "Sync Now" button.
- **Time evidence:** at each online sync, the app saves the server time and the phone's uptime. Offline events then get an estimated true time that isn't affected if the phone's clock is changed.
- Records stay unsynced for at most 72 hours. Older records are marked "Late Sync".

## 7. Duplicate Prevention

- Each record gets a unique transaction ID generated on the phone. The server ignores repeated uploads of the same ID.
- Only one check-in and one check-out per staff member per day are allowed.
- A repeat scan within 10 minutes shows "Already marked" and isn't stored.

## 8. Check-in / Check-out

- **Check-in:** Scan QR → Photo → GPS → Arrival time
- **Check-out:** Scan QR → Photo → GPS → Departure time
- The system automatically calculates:
  - Late arrivals
  - Early departures
  - Working hours
  - Missing check-ins
  - Missing check-outs
  - Absences
- School start and end times are set by the admin.

**Example daily report**

| Staff | Arrival | Departure | Working Hours | Status |
|---|---|---|---|---|
| Teacher A | 07:35 | 01:45 | 6h 10m | Present |
| Teacher B | 07:52 | 01:50 | 5h 58m | Late |
| Teacher C | 07:40 | 01:30 | 5h 50m | Present |
| Teacher D | 08:15 | — | — | Missing Check-out |

> **💡 Suggestions (optional, for later)**
> - Grace period (e.g. 10 minutes before marking "Late").
> - Different timings for Fridays or separate staff groups.
> - Holiday calendar, so Sundays and holidays aren't counted as absent.
> - Leave requests from the app, approved by the admin.
> - An alert to the admin at closing time listing missing check-outs.

## 9. Admin Web App (GitHub Pages)

- Built with React + Vite. It is hosted at `https://<username>.github.io/<repo-name>/` and redeployed automatically on every push.
- It is a static site, so all admin actions (create staff, reset password, regenerate QR, device management) run as **Supabase Edge Functions** that verify the user is an admin.
- The Supabase **service role key is never** placed in the web app or the repository.
- **Dashboard:**
  - Total staff, present, absent and late
  - Currently on campus
  - Pending offline records
  - Flagged records (Out of Range, Fake GPS, Old QR, Duplicate Photo, Late Sync)
- **Staff management:**
  - Add, edit and deactivate staff
  - Reset passwords
  - Manage devices
- **Attendance:**
  - Daily and monthly views
  - Photo viewer showing the original and overlay side by side
  - Map pin for each record
  - Manual correction, which requires a reason
- **QR management:**
  - Regenerate QR
  - Download the A4 PDF
  - View QR version history
- **Settings:**
  - Academy location and radius
  - School timings
- **Audit log:** every correction, device change and QR regeneration is recorded automatically by database triggers.

## 10. Reports

- Individual staff report
- Daily attendance sheet
- Monthly summary
- Late-arrival report
- Working-hours report
- All reports show GPS distance and status.
- All reports export to Excel and PDF.

## 11. Supabase Free Plan and 1-Month Data Removal

"Staff data removed after 1 month" applies to attendance records and photos. Staff accounts are kept so staff can still log in.

- **Every night, a scheduled job deletes:**
  - Photos older than 30 days
  - Detailed attendance records older than 30 days
- **Kept permanently:** a small monthly summary table per staff member (days present, lates, absences, hours).
- **Storage estimate for 30 staff:**
  - Each day: 2 events × 2 photos × about 150 KB ≈ 18 MB
  - Over 30 days: about 470 MB, within the 1 GB free storage
  - With more staff, reduce the photo size.
- **Free-plan limit:** a project pauses after about a week without activity. Daily attendance keeps it active, but during long vacations the admin should open the dashboard once a week.

## 12. Backup

The free plan has no automatic backups, so:

- **Weekly automatic backup:** the database is exported to the admin's Google Drive via a GitHub Actions job (`weekly-backup.yml`).
- **Before monthly deletion:** the full month's report is generated automatically and stored as Excel and PDF.
- **Manual option:** a "Download full backup" button in the admin web app.

## 13. GitHub Build and Distribution

### Repository structure

```
attendance-system/
├── android-app/          # Kotlin app
├── admin-web/            # React (Vite) admin panel
├── supabase/             # SQL, RLS policies, Edge Functions
└── .github/workflows/
    ├── deploy-admin.yml
    ├── build-apk.yml
    └── weekly-backup.yml
```

### Important rules

- Free GitHub Pages requires a **public repository**, so no secrets are ever committed to it.
- The Supabase anon key may be public only if Row Level Security (RLS) is set on every table.
- All keys and passwords are stored in **GitHub Secrets**.

### Workflow 1 – Deploy admin web to GitHub Pages

`.github/workflows/deploy-admin.yml`

```yaml
name: Deploy Admin Web
on:
  push:
    branches: [main]
    paths: ['admin-web/**']
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Install and build
        working-directory: admin-web
        run: |
          npm ci
          npm run build
        env:
          VITE_SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
          VITE_SUPABASE_ANON_KEY: ${{ secrets.SUPABASE_ANON_KEY }}
      - uses: actions/upload-pages-artifact@v3
        with:
          path: admin-web/dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

**Notes:**
- In `admin-web/vite.config.js`, set `base: '/OnTime/'` (your repo name).
- Use `HashRouter` in React so page refreshes don't return a 404.

### Workflow 2 – Build APK

`.github/workflows/build-apk.yml`

```yaml
name: Build APK
on:
  push:
    branches: [main]
    paths: ['android-app/**']
    tags: ['v*']
  workflow_dispatch:

permissions:
  contents: write

jobs:
  build:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: android-app
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17
      - uses: gradle/actions/setup-gradle@v4

      - name: Decode signing keystore
        run: echo "${{ secrets.KEYSTORE_BASE64 }}" | base64 -d > release.jks

      - name: Build release APK
        run: ./gradlew assembleRelease
        env:
          KEYSTORE_PATH: ${{ github.workspace }}/android-app/release.jks
          KEYSTORE_PASSWORD: ${{ secrets.KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.KEY_PASSWORD }}
          SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
          SUPABASE_ANON_KEY: ${{ secrets.SUPABASE_ANON_KEY }}

      - uses: actions/upload-artifact@v4
        with:
          name: attendance-apk
          path: android-app/app/build/outputs/apk/release/*.apk

      - name: Publish release (on version tag)
        if: startsWith(github.ref, 'refs/tags/v')
        uses: softprops/action-gh-release@v2
        with:
          files: android-app/app/build/outputs/apk/release/*.apk
```

### Signing config – `android-app/app/build.gradle.kts`

```kotlin
android {
    signingConfigs {
        create("release") {
            storeFile = file(System.getenv("KEYSTORE_PATH") ?: "release.jks")
            storePassword = System.getenv("KEYSTORE_PASSWORD")
            keyAlias = System.getenv("KEY_ALIAS")
            keyPassword = System.getenv("KEY_PASSWORD")
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")
            isMinifyEnabled = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }
}
```

### One-time setup

1. Create a signing keystore once with `keytool`, then convert it with `base64 release.jks`.
   - **Keep the original file safe.** If it is lost, installed apps cannot be updated, and every phone must uninstall, reinstall and re-bind its device.
2. In the repo, go to **Settings → Secrets and variables → Actions** and add:
   - `KEYSTORE_BASE64`
   - `KEYSTORE_PASSWORD`
   - `KEY_ALIAS`
   - `KEY_PASSWORD`
   - `SUPABASE_URL`
   - `SUPABASE_ANON_KEY`
3. Go to **Settings → Pages → Source** and select "GitHub Actions".

### How staff get the app

- Every push to `main` builds a test APK, downloadable from the **Actions** tab.
- Pushing a version tag (e.g. `v1.0`) publishes the APK on the **Releases** page as the official download link.
- Staff install the APK after allowing "Install unknown apps".
- *Optional:* the app checks the latest GitHub Release and prompts staff to update.
